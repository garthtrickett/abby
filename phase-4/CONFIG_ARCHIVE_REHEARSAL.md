# Configuration archive rehearsal, version 0.1

**Status:** A configuration-only slice of Phase 4 passes locally. The full acquisition rehearsal and Phase 5 cutover remain open.

`buildPostgresTenantConfigArchive` reads every explicitly mapped location in one tenant under a single repeatable-read PostgreSQL snapshot after a host-owned authorization/audit callback. It exports location mappings, versioned policy and clinic automation settings, write-stop history, and approved/revoked knowledge into the [portable archive](../phase-0/PORTABLE_ARCHIVE_CONTRACT.md). It rejects an unmapped location or clinic, duplicate target mapping, mixed target tenants, pending routing, or orphaned in-flight write records. In standalone-minimal mode, completed strict text calls with valid event sequences and no side work are omitted with only a tenant-wide count; active or rich calls fail. Reference-mode rehearsal still requires zero calls. Unknown policy fields are omitted by an explicit projection. The existing `buildPostgresConfigArchive` one-location API uses this snapshot builder and still rejects any other source location. `decodeTenantConfigArchive` verifies the whole archive and groups its policy and knowledge by location and automation/write-stop history by clinic; it rejects cross-scope records even when the section digest is valid.

`ReferenceConfigArchiveImporter.preflight` authorizes inspection, verifies and materializes the exact archive bytes, validates section semantics and required host references, and returns source counts plus each mapping decision without staging target state. `stage` repeats that validation against current target state and stages native reference policy, knowledge, and ledger stores. It retains the source history and a count/digest/mapping receipt. Imported automation and booking are off, every formerly executable capability is at most request-only, and the target ledger is write-stopped. A repeated archive/digest returns the original staged result; the same ID with different bytes or a different archive for the same target is rejected. Staging does not publish a phone route.

`ReferenceTenantConfigArchiveImporter` applies the same checks to all locations before creating one shared reference policy, knowledge, and ledger composition. One source clinic must map to one target clinic, and two source clinics cannot silently merge into one target clinic. A single clinic automation version is visible at every imported location in that clinic. Preflight leaves the target free; staging records per-location counts and mapped references, turns booking and automation off, and stops writes for each target clinic. The PostgreSQL-to-reference E2E runs synthetic knowledge calls at two locations and checks shared automation changes, replay, collision, missing-reference, and clinic-mapping failures.

`comparePostgresConfigArchiveSource` takes a new audited source snapshot with a new archive ID and compares its schema, omitted-call count, and exact section count/byte/digest markers with a verified baseline. It detects mapping, setting, knowledge, or completed text-call-count drift; a newly active or rich call makes the snapshot fail. An unchanged result means only that the two snapshots contain the same portable configuration and omission count; a later write remains possible until a host-owned quiescence fence is established.

The [PostgreSQL source quiescence fence](SOURCE_QUIESCENCE_FENCE.md) provides a durable write barrier for a configuration-only tenant with no calls or only completed strict text calls. A [fenced final archive](FENCED_FINAL_ARCHIVE.md) binds the exact frozen version into the archive and import receipt, and a fresh fenced source comparison checks exact section contents and omission count. The archive and comparison APIs remain usable for ordinary dry runs without a fence; a final cutover must verify the fence version again when changing route ownership.

The [durable PostgreSQL target importer](DURABLE_TARGET_IMPORT.md) stages this same configuration-only archive into native target policy, knowledge, and write-stop tables. Its receipt and full source configuration history survive a process restart. The import transaction rejects occupied tenants and serializes concurrent stages; it leaves all target automation and writes stopped and does not publish a route.

The PostgreSQL-to-reference E2E in `test/storage/postgres-config-archive.test.ts` covers a side-effect-free preflight, complete mapped-reference decisions, multiple policy and knowledge versions, a pristine source with no setting rows, source execute-mode restriction, current knowledge in a new embedded synthetic call, next-version continuation after excluded draft versions, idempotent and concurrent import replay, changed-manifest conflict, valid-digest semantic tampering, missing setting sequence, source-snapshot drift, and secret-canary exclusion. A strict standalone HTTP availability journey checks that a completed call exports with one omission and no caller text, Cliniko appointment detail, or call ID; it also scans the database and disposable backup. The archive-envelope suite covers changed streams between verification and import. Run `npm run probe:postgres` for the disposable migrated-database proof and `npm test` for the memory suite.

The reference fixture remains in memory; the PostgreSQL target importer is a concrete durable adapter for the configuration-only path. A buyer with a different database must implement the same atomic native import and receipt contract. A [synthetic number cutover](../phase-5/CONFIG_ONLY_NUMBER_CUTOVER.md) now stages, publishes, and rolls back one host-owned route with the frozen source and staged target bound under database locks. Retained call/action records, retention/consent eligibility, unresolved imported staff work, and prompt version material are still absent from this slice. The source fence does not cover Cliniko or an external carrier. Neither the Phase 4 nor Phase 5 exit gate is met.
