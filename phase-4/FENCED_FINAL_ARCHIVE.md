# Fenced final configuration archive, version 0.1

`buildPostgresFencedTenantConfigArchive` requires an exact positive source fence version. After host authorization and audit, its repeatable-read transaction takes the source tenant's shared portability lock, reads the fence row, and rejects an unfrozen or different version before reading configuration. The version is included in the archive manifest, so the manifest digest binds it to the exported section counts and hashes. Ordinary `buildPostgresTenantConfigArchive` calls remain useful for unfenced dry runs.

The archive decoder carries `sourceFenceVersion` into tenant and one-location data. Reference preflight receipts and the durable PostgreSQL target import receipt retain it, together with the source history. `comparePostgresFencedTenantArchiveSource` authorizes a fresh export under the same fence version, validates every source/target mapping, and compares schema and all five exact section count/byte/digest markers. The PostgreSQL E2E proves that export fails before freeze, with a wrong version, and after release; the accepted version survives decode and target import. It also proves that a digest-valid old archive with a forged fence number fails the fresh content comparison.

This is evidence about the source at the instant of the snapshot. It is **not** a live claim that the source is still frozen: the [synthetic cutover](../phase-5/CONFIG_ONLY_NUMBER_CUTOVER.md) requires an `unchanged` fresh comparison, then acquires the source tenant lock and rechecks the same fence version when it changes one database-owned number assignment. A digest by itself does not authenticate an archive supplied to the buyer. The fence still excludes real Cliniko activity, external phone routing, and schema migrations. This configuration-only path refuses any call or pending routing history; retained-call cutover needs the separate consent and retention work.
