# PostgreSQL source quiescence fence, version 0.1

The configuration-only acquisition rehearsal can now freeze an unused Abby tenant before its final source archive. `PostgresPortabilityFence.freeze` requires a host authorization and durable audit reference, then takes an exclusive tenant advisory lock, checks that there are no call, pending-location, or orphaned in-flight write rows, and commits a versioned `frozen` state plus an audit event. `release` requires the current version and a separate audited request. Replaying the same request returns its stored result; an old freeze request cannot refreeze after release.

Migration `011_portability_fence` guards writes to every current operational Abby tenant table, including settings, knowledge, calls, pending location calls, events, effects, staff work, write-stop state, and effect leases. A write takes a shared tenant advisory lock and checks the durable fence row. This lets different tenants and same-tenant ordinary writes proceed concurrently; a freeze waits for earlier writes to commit before it takes effect. A writer with an older repeatable-read snapshot fails closed. Direct SQL writes and `TRUNCATE` cannot bypass the guard. The fence and audit tables are owned by the embedding host's administrative database role; the write guard checks them through a security-definer function with a fixed search path, so an ordinary application role does not need table-write permission.

The disposable PostgreSQL E2E freezes a source tenant, proves the archive stays unchanged while attempted policy, knowledge, call, pending-location, and direct SQL mutations fail, then releases the fence and observes settings drift. A two-location archive proves that one tenant fence covers both locations. Other cases prove that an in-flight write commits before freeze and an older repeatable-read writer cannot commit after freeze. The [fenced final archive](FENCED_FINAL_ARCHIVE.md) now records the exact frozen version inside the exported manifest and target receipt. Run `test/storage/postgres-portability-fence.test.ts` through `scripts/with-postgres.sh` after migrations, or use `npm run probe:postgres` for the full disposable database gate.

This fence currently refuses **any** call history, matching the configuration-only exporter; orphaned in-flight evidence returns the distinct `unresolvedWork` failure. It does not freeze Cliniko, a telephone route, another application using the same Cliniko account, the host's own mutable tables, or schema migrations. The host must pause migrations during cutover. Retained call/action export, consent and retention eligibility, final route switch, and rollback remain Phase 4/5 work. A final cutover orchestrator must hold and recheck this exact fence version while publishing the target route; an ordinary archive comparison alone is not a route-switch proof.
