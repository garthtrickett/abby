# OpenAI speech synthesis adapter, synthetic proof

`OpenAISpeechSynthesis` implements Abby's `SpeechSynthesisPort`. It requests `response_format=pcm` and `stream_format=audio` from the [OpenAI Speech API](https://developers.openai.com/api/docs/guides/text-to-speech). The documented raw stream is mono signed 16-bit little-endian PCM at 24 kHz. The adapter converts it in memory to Abby's mono 16 kHz PCM, emits bounded 20 ms chunks, and carries a partial sample and resampling position across arbitrary HTTP chunk boundaries. It does not save approved text or audio. The server supplies the API key; it never enters a browser response or error message.

Abby still owns the voice session, policy, delivery state, and playback acknowledgment. A successful Speech API response or a queued audio chunk is not evidence that the caller heard anything. Only the authenticated output transport's exact final-chunk completion can settle `played`. Failed HTTP responses, malformed or oversized audio, and cancellation fail without claiming playback. The synthetic E2E uses a fake streaming HTTP response and the real `StreamedPlaybackPort` to check this boundary, including a denied request and odd-byte audio. A second memory/PostgreSQL journey injects the adapter into `ConnectedVoiceCall` and checks that its durable greeting remains `started` until output evidence changes it to `played`.

This adapter is optional. The [live synthetic speech-loop baseline](../eval/LIVE_BASELINE_2026-09-29.md) now exercises it against the actual Speech API and replays its in-memory output through the production transcription adapter. The baseline found 30-second synthesis failures for `gpt-4o-mini-tts` on both `coral` and `marin`; a small `tts-1` comparison completed, but does not establish quality or pilot reliability. Before live caller use, prove provider latency and audio quality on representative calls, cancellation and interruption through the signed media transport, key and retention policy, clinic consent configuration, and caller-facing voice disclosure where required. The adapter does not satisfy the Phase 0 media proof or Phase 1 live-call gate by itself.

## Opt-in first-chunk fallback

`ClinikoVoiceServerConfig.openai.speechFallbackModel` enables a second Speech API model for the standalone server. The default leaves it disabled. When enabled, the server gives the primary model 1,500 ms to produce its first valid PCM chunk, then aborts that request and starts the alternate model. `speechPrimaryFirstChunkMs` can change that bound. The playback port allows 5,000 ms for the combined first-chunk attempt by default; `playbackOptions.firstChunkDeadlineMs` can change it, but must exceed the primary bound. Later chunks and output sends keep the existing 2,000 ms step bound unless `stepDeadlineMs` is explicitly configured. Invalid bounds refuse server preparation or call setup.

The alternate model may start only before any audio chunk has reached output. A caller interruption cancels the pending primary without starting the alternate. Once the primary produces its first chunk, later primary errors remain uncertain playback failures: Abby clears output and never splices speech from a different model into the same utterance. The same approved, patient-free presentation text is passed to either model; audio remains transient. `E2E-151` exercises the signed local standalone socket with a stalled primary and checks that only alternate audio is queued, while port tests cover interruption and post-output failure. The test does not establish real Twilio audio delivery, first-response p95, spoken quality, or a clinic's consent to use the alternate voice.

An [opt-in signed local live evaluation](../eval/README.md#signed-local-live-speech-evaluation) also runs the actual Speech API through the standalone server and synthetic Twilio WebSocket. It checks that non-silent G.711 media and a completion mark traverse the composed path, with an isolated database canary scan. It remains a local simulation of Twilio output, not real caller playback evidence.

The [repeated first-chunk timing runs](../eval/LIVE_BASELINE_2026-09-29.md#repeated-first-chunk-fallback-timing) exercised 56 patient-free utterances across two small batches with no failed queues or first queued chunks over five seconds. The fallback selected 15 times. Their queued-only p95 values are evidence about this account and synthetic output port, not a measured caller first-response percentile or voice-quality approval.
