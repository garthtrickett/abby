# Account-scoped clinic number routing

`ClinicNumberRoutingHost.identifyCall(accountRef, dialedNumber)` identifies the tenant, clinic, candidate locations, and route version before mutable automation policy is read. The host owns its number directory, so an embedded clinic can use its existing routing table. The reference host provides fixed assignments for synthetic tests. `ClinicPolicyRouter` validates the host's echoed account and number, clinic identity, route version, and unique candidate locations. It reads location policy only when exactly one location is identified and checks that the returned policy is bound to that location.

`CallAdmissionService` now passes the authenticated provider account to its policy resolver. Its global call-key lookup still happens first. A duplicate webhook receives the stored receipt even if the number directory has since changed; a changed dialed number under that call key is a conflict. The captured policy records `numberRouteVersion`. The same phone number under two provider accounts can resolve to different tenants without sharing a call ID or clinic policy.

Unknown numbers, ambiguous clinics, malformed host identity, and a number with multiple candidate locations never guess a clinic or location. The first three produce a typed routing failure. Multiple locations produce `locationChoiceRequired`. `AdmissionFallbackCoordinator` sends these failures through the independent provider fallback and operational alert, with no Abby call or location-specific policy read.

For a shared number, `ClinicPolicyRouter.identify` exposes the host's candidate location IDs without reading location policy. After the caller chooses, `resolveSelected` reidentifies the authenticated account and dialed number. It checks the captured tenant, clinic, route version, and selected candidate before reading that location's policy. An unlisted location returns `invalidLocationChoice`; a changed clinic or route version returns `staleLocationChoice`. Neither failure admits a call or silently falls back. The call controller can ask again or hand off. A selected policy can be admitted through the existing `CallAdmissionService`, which captures the chosen scope and number route version.

The [pending-location reservation](PENDING_LOCATION_RESERVATIONS.md) durably holds the provider call key and candidate locations before a choice, and the [shared-number intake controller](SHARED_NUMBER_INTAKE.md) can bind a trusted synthetic choice to the call. A pre-location session lease and caller-facing voice prompt are still required for `E2E-055`. Entry points using ordinary admission still send shared numbers to independent fallback.

The memory and PostgreSQL synthetic journeys cover unknown-number fallback, ambiguous-clinic fallback, account isolation, route-version capture, shared-number fallback, chosen-location scope isolation, invalid and stale choices, and a replay after reassignment. No live number, provider authentication adapter, or tested provider-owned fallback is present.
