# Transient voice presentation content

`VoiceSession` has an optional transient-content mode for a call whose durable presentation rows contain status and opaque IDs but no speech text. Its constructor receives the approved greeting for the admitted scope. Before activating the session it checks that the greeting version and owner match the admitted policy snapshot; if the stored snapshot still contains text, that text must also match. A mismatch leaves the call in `starting` and sends no audio.

After a successful caller turn or effect drain, the live session remembers only the current pending notice or speech text in process memory. On dispatch it uses that text, never `approvedText` from a ledger read. Exact playback completion, interruption, disconnect, lease loss, and failed delivery discard the remembered text. If the live text is missing, the session ends the call with `mediaFailure` and reports `transportUnavailable`; it cannot recover speech by replaying a database field. This is an intentional fail-closed result after process loss. The host must route the caller to its proven provider-owned fallback before enabling live traffic.

`E2E-133` exercises greeting and patient-specific booking-detail playback while a ledger adapter redacts every presentation read. It also injects a pending notice whose content the live session never saw and proves no second audio is queued. The same test is designed to run against memory and disposable PostgreSQL reference ledgers. This proves the session interface, **not** safe PostgreSQL storage: the reference ledger still writes the original rich call state. The [standalone transient composition](STANDALONE_TRANSIENT_VOICE.md) now proves that a synthetic call can avoid voice database writes entirely, but durable admission, crash recovery, independent fallback, logs, and archive coverage remain release gates. No standalone patient call is permitted yet.
