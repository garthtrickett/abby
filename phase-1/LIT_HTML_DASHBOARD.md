# Standalone lit-html dashboard shell, version 0.1

The standalone browser uses direct `lit-html` `html` and `render` calls. A small controller reads permitted capabilities, displays the current booking and after-hours settings, submits versioned changes, and reads a scoped call summary by exact call ID. Templates receive typed UI state and event handlers; they contain no booking or provider rules. The browser fetch adapter handles transport faults and malformed replies as typed failures. The server calls the same `CommandGateway` that agents and an embedded host use.

The generic full dashboard also offers a clinic-admin greeting editor and audit. It accepts exact public text, a version and bounded effective dates, then binds the approval owner to the authenticated actor through `settings.routing.greeting.change.v1`. Disable records a separate setting change and removes the greeting from new call snapshots. `E2E-245` covers the browser and synthetic call behavior, including expired values. The supervised standalone Cliniko panel exposes the same greeting command and audit beside availability setup through a restricted HTTP path; `E2E-246` covers browser, durable listener and signed synthetic voice behavior, including refusal when stored text omits required keypad choices. `E2E-247` rejects unusable one-day or seven-day wording at local approval, preserves the rejected form for correction, and retains call-time refusal for direct policy edits.

`CallReview` projects a call into lifecycle, version, action kinds/statuses, and staff follow-up reasons/statuses. It omits patient references, approved speech, provider payloads, and full call state. The gateway binds the actor's location scope before reading. A clinic administrator may change booking or approve public after-hours information; the after-hours approval owner comes from the authenticated actor. Staff can view settings and call summaries but cannot submit either change command or read admin setting history. Ordinary setting changes affect new calls through their captured policy snapshot. The after-hours control is shown as inactive when live transfer or staff follow-up is unavailable.

Run `npm run demo:dashboard` to start the loopback-only reference dashboard at `http://127.0.0.1:3400` with an in-memory clinic and a synthetic call ID `demo-call`. Run `npx playwright install chromium` once, then `npm run test:browser` for parallel Chromium journeys. The browser journeys cover default, enabled, disabled, page reload, next-call capability, tenant isolation, stale-version refresh, scoped call review, and view-only denial through the HTTP command path. `npm test` and `npm run probe:postgres` cover the typed command and ledger paths separately. Browser E2E runs as its own parallel CI job.

The dashboard also has a separate lit-html clinic availability setup panel when its bound actor has `clinic.availability.approval.change.v1`. It lists business metadata, inspects one practitioner/type selection, shows the stored approval version, requires explicit confirmation of read-only use, and can approve or revoke the route. Its current-route check reuses call-time route, policy, credential and selected Cliniko catalogue validation and reports a point-in-time eligibility result; every call still rechecks. The local HTTP endpoint accepts its availability setup commands and the public greeting approval/audit commands through the same schema-checked gateway; it requires a loopback socket, exact loopback Host, and same-origin request. `E2E-195` and `E2E-216` cover the browser flow against a synthetic Cliniko catalogue. A stored approval grants no patient action or staff request.

The demo binds a fixed local actor and has no production authentication. `createHostAuthenticatedDashboardServer` is the embedding boundary: the host resolves an actor from its own authenticated session for every request, creates a `CommandGateway` for that exact actor, and supplies a fixed public origin. Abby rejects absent identity, mismatched gateway identity or Host, and POST requests without that exact Origin. No role, tenant or actor value from request JSON or self-declared role headers grants access. `E2E-211` covers this boundary with synthetic host sessions. `createStandaloneClinikoAdminDashboard` composes that boundary with the standalone privacy preflight and durable Cliniko route approval; `E2E-212` proves a separate signed voice runner reads an admin approval and rejects a call after revocation. A deploying host must still select and integrate a real identity source, deploy the appropriate listener, and implement the broader call-review and staff-work screens before clinic use. The local demo uses no live Cliniko data or media and has no Cliniko setup port, so its availability panel stays hidden.

Set a distinct random 64-character lowercase hex `ABBY_ADMIN_ACCESS_TOKEN_HEX` and an opaque `ABBY_ADMIN_ACTOR_REF`; `ABBY_ADMIN_PORT` defaults to `3401`. Run `npm run admin:local` and open `http://127.0.0.1:3401` on the same machine or through an SSH tunnel. At the browser challenge, use username `abby-admin` and the admin token as the password. The listener binds only `127.0.0.1`, loads the dedicated lit-html bundle, exposes availability setup, public greeting approval and audit, settings read, aggregate speech status and clinic-scoped seven-day operational counts over HTTP, and keeps the token, Cliniko key, transcripts and owner-only report paths out of the browser response and Abby database. Keep the token in an owner-only environment file, outside shell history and chat. `E2E-214` checks the local challenge, browser route approval/revocation and durable restart readback with synthetic data; `E2E-246` checks the greeting panel and durable approval/disable. `E2E-233` checks the speech status role boundary, redacted browser response and unavailable-evidence fallback. `E2E-235` checks the admin-only, actor-scoped operational read, malformed-result refusal and PostgreSQL restart readback. The speech panel reads the current owner-only report set through `readSpeechGateStatus`; missing, invalid, stale or insecure reports show unavailable and release unverified. A synthetic placeholder number can rehearse setup before a Twilio number exists; approval must be repeated for the final exact route. This local token does not establish a real clinic staff identity or clinic sign-off.

The panel reports whether the current Cliniko business catalogue could be checked and compares its credential fingerprint with the stored approval. After changing `ABBY_CLINIKO_API_KEY`, restart the local admin listener with the new key, inspect the selected business/practitioner/type, and record a new approval version before testing another call. A stored approval from the old key remains visible for audit but is inactive at signed call admission. `E2E-215` covers the browser warning and the signed refusal/reapproval sequence with synthetic credentials. A matching fingerprint does not certify current appointment availability or clinic sign-off.

### Listener ownership in isolated E2Es

An authenticated host dashboard may set `publicOrigin: "http://127.0.0.1:0"` and bind that same returned server to port zero. The server derives the exact permitted Host/Origin tuple from its own incoming socket's bound loopback port; it never takes an origin from Host or forwarding headers. Port-zero HTTPS origins are rejected. Fixed HTTP/HTTPS origins keep their configured tuple. The test helper `listenLoopbackServer` waits for that server's successful bind and returns its real origin, so browser fixtures no longer reserve and release a different listener's port first.

The actual supervised `admin:local` runner accepts `ABBY_ADMIN_PORT=0` only with `ABBY_ISOLATED_POSTGRES_PROBE=1`, emits its assigned port through child IPC, and prints that assigned port in its startup message. Its restart fixture uses the currently launched child's port. Normal startup still requires a configured port between 1 and 65535 and retains the owner-only loopback identity and exact Origin checks. The signed admin-to-voice fixture obtains its voice port from that voice child's existing `listenerReady` IPC message too. `E2E-249` checks simultaneous dashboard listeners, crossed Host/Origin, missing identity, staff writes, fixed HTTPS behavior and refused non-probe admin port zero, alongside the browser and signed-call journeys. This removes the released-port interval in these fixtures; it does not prove the cause of earlier browser connection resets.

The supervised admin bundle also exposes clinic-wide automation state, enable/disable and paginated audit through the restricted automation command/read routes (`E2E-248`). Local enable remains blocked by unproven readiness. Disabling applies to new calls; it leaves an admitted call's captured policy intact and grants no booking or patient-specific staff capability.

## Cancellation controls

The reference/embedded dashboard exposes cancellation as a separate versioned panel and audit (`E2E-252`). The saved Boolean and effective host capability are shown separately. Only clinic admins may edit or read its history; scope and actor come from the authenticated gateway. Invalid, stale and foreign-origin requests cannot mutate it. If a write outcome and its subsequent reread are both unavailable, controls stay disabled until a reload recovers current state. Admitted calls retain their policy; new calls use the edited value. The supervised standalone Cliniko listener does not expose this patient-action setting, and strict standalone cancellation remains unavailable.

## HTTPS host command boundary

All `/api/` POST routes share one Origin check before body parsing (`E2E-253`). Authenticated hosts require the exact configured scheme, Host and port; forwarding headers cannot substitute another Origin. The local reference server retains its documented optional Origin and loopback boundary. The restricted setup surface is checked separately and cannot expose booking, cancellation or staff actions. A real TLS browser journey checks booking enable/disable, reload, audit ownership, captured policies and staff/foreign-Origin refusal. The test generates and removes its own certificate; production identity, certificates and reverse-proxy deployment remain separate work.

## Rescheduling control

The full reference/embedded dashboard exposes `SET-004` through `settings.appointments.rescheduling.enabled.change.v1` and `settings.appointments.rescheduling.audit.v1` (`E2E-254`). The default is off. A saved value never supplies host permission: only an explicit host rescheduling mode can make it effective, and strict standalone Cliniko mode always reports unavailable. Controls and history use the authenticated admin actor/location. New calls capture edits; admitted calls retain the previous policy. An uncertain edit with an unavailable reread disables controls until reload. The shared HTTPS POST Origin check covers the new route, and the supervised Cliniko availability setup does not expose it.


## Clinic-wide first-time intake

The full reference/embedded dashboard exposes `SET-005` through `settings.patients.firstTimeIntake.enabled.change.v1` and `settings.patients.firstTimeIntake.audit.v1` (`E2E-255`). It compares the clinic intake version, applies changes to new calls at every location of the bound clinic, and keeps location policy edits independent. The default is off. The screen displays raw state and effective host mode; strict standalone Cliniko cannot acquire patient-creation permission through this control. Four browser journeys cover cross-location updates and captured calls, invalid/stale/forged/Origin and role denial, unsupported hosts, and both successful and failed rereads after a lost committed response. The supervised Cliniko setup hides these patient routes. See [the intake contract](../phase-2/CLINIC_FIRST_TIME_INTAKE.md) for persistence and carryover rules and the outstanding release gate.
