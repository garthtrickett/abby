# Configuration-only synthetic number cutover, version 0.1

`PostgresNumberRoutingHost` reads one host-owned PostgreSQL assignment per `(accountRef, dialedNumber)` and supplies the existing `ClinicNumberRoutingHost` port. The directory is a synthetic stand-in for a buyer's number authority; it does not change a carrier or require Twilio. One row and a monotonic route version make one host assignment authoritative at a time, including shared numbers with mapped location choices. The host must keep route and cutover table write permission with its administrative routing role; direct route-table writes by ordinary application roles are outside this reference protocol.

`PostgresConfigNumberCutover.stage` first obtains host authorization/audit, requires an `unchanged` fresh fenced source-content comparison, and checks the staged target import receipt against the exact archive ID, digest, source fence version, and source history. Under source and target tenant locks it rechecks the source fence and native target policy, automation, knowledge, and stopped-write history. Stage records the source and mapped target assignments without changing the live route. Target calls or pending-location calls before publication block the stage or publish step.

`publish` locks both tenants and the route row, checks the exact frozen source version and target import again, and atomically advances that one route to the target. The target check now compares total native settings, automation, knowledge event/head, and write-stop rows across the entire tenant with the rows verified at mapped scopes. Extra configuration under an unmapped target clinic or location blocks publication even if every imported row is still intact. A concurrent or repeated publish returns the same route version. The source fence cannot be released while a cutover is `published`; a database trigger also rejects a direct SQL release. A staged cutover can be discarded without changing the route.

Rollback has two durable steps. `beginRollback` leaves the target route active and records `rollbackPendingRelease`. The source fence can then be released through its existing audited API while the target still owns the number. `finishRollback` requires that release version and atomically advances the route back to the source. If the process stops between steps, the target remains the sole active route and the step can be retried. Work created on the target remains in its ledger and staff queue; rollback never deletes or replays it onto the source. Route events retain actor, audit reference, action, and version.

`test/storage/postgres-number-cutover.test.ts` exercises a two-location shared number through stage, concurrent publish, a target call and staff item, blocked premature release, pending rollback, release, and resumed finish. It verifies the target staff item remains readable afterward. Separate cases reject a stale route version, changed target knowledge, extra target configuration outside the imported scopes, and a source fence released after staging. The PostgreSQL gate also migrates up/down/up and regenerates Kanel types.

This proves the directory and database protocol only. A real number provider or buyer host must supply its own atomic route ownership and observable call admission path. Migration `013_number_cutover` may be down-migrated only in disposable rehearsal databases; a deployed host must preserve route and audit rows and recover forward. The current version 2 exporter omits completed strict text calls with per-location counts sealed against the aggregate, but refuses active, rich, or unresolved source calls, so this rehearsal cannot satisfy the retained-call and unresolved-staff-work import requirements of the full Phase 4/5 exit gates. Product and clinic retention, verification, staff destination, and live media decisions remain required before actual traffic can switch.
