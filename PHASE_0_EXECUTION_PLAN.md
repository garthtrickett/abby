# Abby Phase 0 execution plan

**Status:** Proposed execution plan; product decisions and provider evidence remain open

**Scope:** Phase 0, the contract phase in [PRD.md](PRD.md#12-delivery-plan-and-exit-gates). [TECHNICAL_DESIGN.md](TECHNICAL_DESIGN.md) defines the proposed interfaces and state transitions. This plan orders the work and defines what evidence is required to start Phase 1; it does not replace either document.

## Outcome and working rule

Phase 0 ends with versioned, reviewable contracts for one inbound call, one confirmed appointment action, a staff fallback, and the standalone and embedded compositions. The contracts must express Cliniko, Splose, and an in-process reference host without provider branches in the core. A provider capability may be marked request-only when safe automation cannot be proven and its provider-owned durable staff route is proven; otherwise it is unavailable. That outcome does not block Phase 0; an unproven telephony or durable-intake fallback **does** block voice readiness until a safe route is demonstrated.

Contracts are frozen by version and conformance fixtures, not by forbidding later corrections. An interface change after the gate updates its schema, fixtures, scenario mapping, and migration notes together. An experiment is evidence, not production code or a passing E2E scenario.

### Interim text-first checkpoint

Work on P0-01 to P0-04 and the text, host, typed-error, action, staff, and persistence parts of P0-06 to P0-09 first. Use synthetic caller-turn text, a deterministic reference host, and typed effect receipts to exercise the proposed decisions and failure paths. A test composition may supply a synthetic completed-presentation result to check downstream confirmation rules; it cannot prove that a real transport played audio. Keep that test ingress private to the harness and do not expose it as an agent or production command. [The text test plan](phase-0/TEXT_TEST_PLAN.md) names the initial cases and evidence labels; the [text storage contract](phase-0/TEXT_STORAGE_CONTRACT.md) records the current executable probe and its remaining limits. The [reference host contract](phase-0/REFERENCE_HOST_CONTRACT.md) records the shared standalone and embedded text compositions.

P0-05 and the media-specific portion of P0-07 are deferred while this checkpoint runs. This is a sequencing choice, not a reduction of the Phase 0 exit gate: text-only contract results cannot mark a voice E2E, playback, transfer, or fallback scenario as passed. Resume the media probe before signing off the full Phase 0 gate or claiming live-call readiness. Phase 1 may start a text-driven reference slice only under an explicit partial handoff that leaves voice readiness blocked until its evidence exists.

## Evidence format and decision rules

Each provider or media claim has a stable evidence ID, account/profile and date, operation, precondition, observed result, source or reproducible probe, and a conclusion of **proven**, **disproven**, or **unverified**. Sanctioned synthetic accounts and fixtures are the only test subjects. Credentials and patient data stay out of the plan and evidence bundle.

| Question | Proof required to mark executable or ready | If proof is absent |
| --- | --- | --- |
| Host mutation | Current permission and location/capability are enforced at commit; the offer or target is revalidated; a lost response can be resolved to the exact action key or equivalent definitive evidence without risking a duplicate write | Mark the capability request-only only if a Cliniko-owned durable request/staff route has been proven for standalone mode; otherwise mark it unavailable and use the approved caller fallback without patient-specific Abby work. Record the unsupported or uncertain path and any proven staff destination. |
| Reschedule | Host-native or atomic replacement is demonstrated | Keep the original appointment; request staff follow-up only through a proven Cliniko-owned route in standalone mode, otherwise use the approved caller fallback |
| First-time intake | Approved consent, duplicate check, stable patient ref, and exact write outcome are demonstrated | Request staff follow-up only through a proven Cliniko-owned route in standalone mode, otherwise use the approved caller fallback; never claim an appointment |
| Media playback and transfer | Adapter distinguishes queued from completed playback and requested from connected/failed transfer, and clears queued audio on interruption | Do not enable the affected automated voice behavior |
| Intake and startup fallback | Number-level provider route is test-called while Abby ledger or voice process is unavailable | Block live-call readiness for that number |
| Embedded portability | One reference-host composition can supply host storage, jobs, authorization, patient/diary, and UI through the proposed seams without an Abby server or standalone tables leaking into core | Revise the seam before Phase 1, then update conformance fixtures |

An unverified claim cannot be converted to support merely by an adapter declaration. The product owner approves the expected provider support matrix, including request-only decisions. If actual provider behavior contradicts the proposed technical design, revise the design and its fixtures; do not add a provider-specific branch to ReceptionActions or the SAM acceptor.

## Contract and scenario handoff

The Phase 0 bundle contains four connected artifacts: (1) a versioned contract package and schema/transaction decision tables, (2) a provider and media evidence register with approved support matrix, (3) a scenario manifest and synthetic fixture catalogue, and (4) decision records with the Phase 1 backlog. These may live in focused files as implementation begins; their IDs and cross-links must be stable. The PRD remains product authority and the technical design remains architecture authority.

The manifest now tracks 149 scenario IDs in the technical design, including text-only Cliniko availability and privacy cases E2E-125–127 and E2E-147, and synthetic voice cases E2E-128–146 and E2E-148–149. For each ID, record the requirement, setting or capability where applicable, fixture, observable caller/host/ledger/staff assertions, intended composition, and earliest phase in which it must pass. A planned ID is a commitment to implement a scenario, not a waiver of the PRD rule that a shipped behavior or toggle has a running E2E in the same change. The first Phase 1 slice implements its relevant IDs through production call and command entry points; later slices implement the rest before their behavior ships. Different scenario IDs receive isolated tenant, call, storage, queue, clock, and provider fixtures so CI can shard them. A shared real provider is the only reason to serialize its own narrow group.

The model/voice evaluation corpus records source calls or synthetic variants, exact proposed prompt/model/media configuration, scoring rubric, critical failures, sample and repeat-count decision, and pilot threshold owner. Phase 0 approves the rubric and baseline method; a pilot quality claim requires actual runs against the release configuration in a later phase.

## Phase 0 exit gate

The product and engineering leads sign off only when all of the following are reviewable:

1. P0-01 through P0-09 outputs exist with version IDs, owners, and traceable evidence. Product decisions that affect caller language or safety are approved; any remaining open decision has a conservative Phase 1 route and a date before its dependent behavior is built.
2. The host contract expresses booking, cancellation, request-only rescheduling/intake where proven, and staff handoff for the reference host and both PMS profiles. Exact lost-response reconciliation is required for each mutation classified executable. A standalone Cliniko patient-specific request-only or staff path requires evidence of a Cliniko-owned durable record, staff workflow, and safe lost-response handling; otherwise its mode is unavailable with an approved caller fallback and non-patient operational alert. Each executable provider capability has its required evidence, and unverified ones cannot be promoted to execution in the approved matrix.
3. Media proof covers the transport claims needed by the first Phase 1 voice slice, including actual playback-completion and fallback behavior. Unsupported transport behavior blocks that slice's readiness rather than becoming an invented success result.
4. The typed failure, action receipt, SAM, presentation, lease, consent, staff, and transaction tables agree across the PRD, technical design, and contract package. A replay, correction, uncertain write, and disconnect can each be traced from input to durable state, caller claim, and staff outcome without an unnamed callback or second state owner.
5. A clean disposable PostgreSQL schema probe migrates and generates Kanel/Kysely types without drift; the proposed schema covers global call-key uniqueness and tenant-scoped state while core contracts import no generated row type. The production standalone ledger, outbox, and settings storage are implemented and checked in Phase 1, not counted as complete by this probe.
6. The scenario manifest has no duplicate or unmapped IDs, includes planned settings and failure variants, states observable assertions and earliest passing phase, and defines parallel isolation. No scenario is marked green before its executable test runs.
7. The Phase 1 backlog starts with the minimum production standalone ledger, outbox, and settings storage and an end-to-end call with a safe keyed write in both standalone and reference-host compositions; it names the initial E2E IDs and provider constraints and keeps both compositions on the same core contract.

Record the gate result as **ready**, **ready with request-only capability limits**, or **blocked**. The middle result permits Phase 1 work on proven paths; it does not permit a live clinic pilot. A failed media, fallback, tenant-isolation, or write-safety invariant is blocked for the dependent behavior until corrected and re-proven. The gate report lists remaining uncertainty rather than treating a proposed type as evidence that an external provider satisfies it.
