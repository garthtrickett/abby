# Cliniko reference write mechanisms and carryover

**Inspected:** 2026-10-03. **Reference:** `aeva-ai/aeva-website`, committed `dev` snapshot `60b3ba753ff5299d65262bb69676a5f4f6c1969b`, independently matched to GitHub's `dev` head. The local reference checkout contains unrelated changes and an unfinished merge; all conclusions here use committed objects. This is a source investigation, not a production deployment or live-call observation. No application, test suite, credentials or live Cliniko account was used.

## What the reference establishes

An existing integration can implement booking, cancellation and in-place rescheduling using ordinary Cliniko HTTP writes plus validation, post-write inspection, local deduplication, retries and staff notifications. A written provider guarantee is not a prerequisite to implementing and testing such a practical integration.

The inspected paths do not supply atomic interval exclusion, a conditional confirmed-target mutation or an exact provider commit receipt shared atomically with local recovery state. Those are stronger requirements in [Abby's current activation contract](../../phase-2/CLINIKO_WRITE_ACTIVATION.md). Copying this implementation would not establish those requirements or authorize the additional durable patient data it uses.

[Booking client](https://github.com/aeva-ai/aeva-website/blob/60b3ba753ff5299d65262bb69676a5f4f6c1969b/server/src/services/postcall/bookAppointment/bookAppointmentService.ts#L111), [adapter headers](https://github.com/aeva-ai/aeva-website/blob/60b3ba753ff5299d65262bb69676a5f4f6c1969b/server/src/services/pms/adapters/clinikoAdapter.ts#L102). ## Outcome findings

- The booking resolver converts failed conflict inspection into `confirmedConflict=false`; this can keep a booking without a verified conflict result. That is an intentional source policy, not evidence that conflicts were absent.
- The booking compensation helper catches cancellation errors, while its caller can still store `conflict_cancelled`. A cancellation attempt is not a proven cancellation. [Helper](https://github.com/aeva-ai/aeva-website/blob/60b3ba753ff5299d65262bb69676a5f4f6c1969b/server/src/services/postcall/bookAppointment/bookAppointmentService.ts#L1609), [outcome](https://github.com/aeva-ai/aeva-website/blob/60b3ba753ff5299d65262bb69676a5f4f6c1969b/server/src/services/postcall/bookAppointment/bookAppointmentService.ts#L391).
- Adapter rescheduling returns `conflict_detected_reverted` even when the revert throws. A failed conflict read follows an already successful PATCH and returns failure without establishing that the original appointment is intact. [Result handling](https://github.com/aeva-ai/aeva-website/blob/60b3ba753ff5299d65262bb69676a5f4f6c1969b/server/src/services/pms/adapters/clinikoAdapter.ts#L1030).
- Retrying an ambiguous create after releasing the processing row can duplicate a remotely committed appointment. This is a source-derived risk, not an observed production duplicate in this investigation.
- A failure after a successful provider create but before recording local completion can also enter retry/release handling; a stranded local `processing` claim has no inspected recovery/takeover mechanism. Local deduplication and a provider commit are not one transaction. [Completion and catch](https://github.com/aeva-ai/aeva-website/blob/60b3ba753ff5299d65262bb69676a5f4f6c1969b/server/src/services/postcall/bookAppointment/bookAppointmentService.ts#L466), [processing claim](https://github.com/aeva-ai/aeva-website/blob/60b3ba753ff5299d65262bb69676a5f4f6c1969b/server/src/services/postcall/bookAppointment/idempotencyService.ts#L18).
- The Cliniko capability declares `rescheduleFailureGuaranteesUnchanged`; timeout and failed-compensation paths do not establish that blanket guarantee. The direct handler's explicit unknown/failed-revert handling should not be conflated with the adapter's misleading reverted label. [Declaration](https://github.com/aeva-ai/aeva-website/blob/60b3ba753ff5299d65262bb69676a5f4f6c1969b/server/src/services/pms/pmsProviderCapabilities.ts#L84).

## Privacy and carryover

The reference persists call-ID/appointment/outcome records in PostgreSQL, complete booking retry payloads in Redis/Bull, dead-letter payloads, validation evidence and patient-specific notification/retry context. Cancellation retry payloads contain appointment ID, patient ID, offered time/practitioner, caller phone, patient first name and appointment display date. [Cancellation retry data](https://github.com/aeva-ai/aeva-website/blob/60b3ba753ff5299d65262bb69676a5f4f6c1969b/server/src/services/postcall/handlers/cancelRetryService.ts#L58), [booking dead letters](https://github.com/aeva-ai/aeva-website/blob/60b3ba753ff5299d65262bb69676a5f4f6c1969b/server/src/services/postcall/bookAppointment/retryService.ts#L97).

Abby's D-06/D-11/D-12 do not permit those patient-specific stores in its standalone database, queues, logs or backups. An authorized embedded buyer may own the corresponding state, subject to its host contract. A phone-to-patient-ID index is not an equivalent recovery ledger.

Carry over exact target/duration handling, in-place moves, scoped policy, read-only diagnostics, meaningful failure cases and explicit notification ownership. Keep provider uncertainty distinct from rejection, and never label failed compensation as completed. Durable retries/replay belong only in a permitted owning host, with its own loss semantics. Cross-site collision acceptance, fail-open conflict inspection and automatic cancel/revert are clinic-visible policies; this comparison does not approve them for Abby.

The existing [gap analysis](../../AEVA_ABBY_CORE_CLINIKO_GAP_ANALYSIS.md) remains an older broader snapshot. This map supplements its write-specific evidence; it does not upgrade its other feature or production claims. The standalone implementation can continue through known API adapters and synthetic/demo tests. The additional atomic/no-overlap and privacy-preserving cross-process recovery guarantees remain unestablished by the reference source.

## Review evidence and limits

Two independent read-only investigation agents traced booking/recovery and appointment changes respectively. Their reports were cross-checked against pinned committed source before this map was assembled. This covers the identified reception-call, multi-action, retry, compensation and deposit-expiry appointment writers; it is not a proof that the entire repository or Cliniko service has no other mutation path or undocumented stronger capability. No runtime test or provider guarantee was inferred from a function name, comment or successful-looking result label.
