# Use exact provider acknowledgements for external booking success

Revise only the individual and native class creation provisions of [ADR 0001](0001-standalone-cliniko-write-contract.md): finish authorization, provider-owned review and other preparation before final exact availability, send once, and preserve a validated native acknowledgement as booking success despite later observation or notification failure. This accepts the external provider's remaining races without a post-write veto; unacknowledged writes retain owned review and no automatic replay. Cancellation, rescheduling, registration/correction, resends, class movement/pass relinking and an owning diary's stronger transactional guarantees retain their operation-specific contracts.

The owner instructed execution of [the ordered plan](../../phase-2/EXECUTION_ORDER.md) on 16 October 2026. Delivery is staged under the [booking plan](../../phase-2/PROVIDER_ACKNOWLEDGED_BOOKING_PLAN.md): the receipt foundation binds the full individual interval, and the next individual runtime patch completes preparation before online/roster availability and establishes success at the validated acknowledgement. A narrow in-process acknowledgement notification preserves that result through host, review and worker cancellation; ordinary result/action/lease validation still applies. No post-write GET, conflict veto, compensation or automatic review closure belongs to individual creation's success path.

The class runtime step applies the same success policy to native attendee creation, with an explicitly approved case/pass when applicable. Permission, entitlement/history, metadata, proof, SAM and quota preparation precede the final complete double occurrence/attendance observation. Only synchronous original expiry, local proof/lifetime and request checks remain before dispatch. The exact bounded HTTP 201 must bind native attendee/self, patient, occurrence, action marker, active state and requested case. There is no mandatory post-create attendee, capacity or pass-use inspection; a later over-capacity, duplicate or consumption race cannot erase the established creation result. Payment and atomic capacity/pass exclusion are not established.

For ordinary creation, the optional case field may be absent; this acknowledges creation without claiming the attendee is unlinked. Any returned case without approval, including an undocumented null/empty shape, is nonexact. A move that requires an unlinked replacement still uses the documented native null-filter inspection under its existing contract; omission in a creation response cannot satisfy that stage. Class cancellation, movement and case linking continue through their separately inspected operations.

This scoped decision approves neither a clinic, recovery workflow nor deployment. Standalone phone-to-patient-ID-only persistence and Cliniko-owned pre-send review remain unchanged. Source delivery, exact-head CI/independent review and activation acceptance are separate evidence; see [the progress ledger](../../phase-2/EXECUTION_PROGRESS.md).
