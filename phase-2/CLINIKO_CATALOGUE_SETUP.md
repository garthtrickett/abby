# Cliniko catalogue selection contract

`ClinikoCatalogueReader` lists bounded business metadata and checks one business, practitioner, and appointment type. Its `candidate` result means the selected metadata currently appears eligible for online availability reads. It never grants booking, patient disclosure, or staff-request authority.

`ClinikoCatalogueSetup` supplies the host-facing confirmation seam. The host provides an authenticated `HostActor`, account-scoped number routing, a versioned location policy, and a compare-and-swap approval store. Only a clinic admin for the reader's exact tenant, clinic, and location can list or approve. Approval requires a single-location route with the expected account, dialed number, and route version; the selected policy version; an eligible Cliniko snapshot no more than 60 seconds old; and a current credential fingerprint. Route and policy are checked before and after the provider reads. Concurrent changes to the approval record fail by version conflict.

An approval stores only clinic configuration: scope, selected Cliniko IDs, route and policy versions, key fingerprint, approver's opaque reference, and timestamps. It fixes both patient action and patient-specific request modes to `unavailable`. This is a clinic administrator's permission to use one read-only availability route. It is separate from Cliniko's API permissions and from a clinic's later approval of any patient-specific staff workflow. `readApprovedRoute` checks the stored approval, exact number route, policy version, key fingerprint, and revocation version before voice ingress without contacting Cliniko. `resolveForCall` additionally rechecks provider eligibility before using the selected catalogue. These reads are sequential, so they cannot guarantee that Cliniko will not change after the final check. The availability reader checks the current online-booking flags before speaking times and preserves a truthful direct-contact fallback if they change. Available times remain provisional.

`MemoryClinikoApprovalStore` is a reference adapter and loses approvals on restart. `PostgresClinikoApprovalStore` keeps an append-only, clinic-scoped approval/revocation history with scalar, constrained configuration fields and transactional compare-and-swap. It stores neither the API key nor patient content. The standalone voice runner now reads that PostgreSQL approval at signed webhook admission and call binding. Missing, changed, or revoked approval rejects the next call before a Cliniko read; an already active call retains its captured policy. A production host still needs an authenticated clinic identity source and must use the host-facing confirmation flow before real deployment. The current synthetic test actor and seeded approval do not establish a real clinic's consent. A demo-account read of the new catalogue and a real clinic's confirmation of its selection and caller wording are still required. The current configuration archive and buyer cutover do not transfer these approval records.
