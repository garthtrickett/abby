# Cliniko catalogue selection contract

`ClinikoCatalogueReader` lists bounded business metadata and checks one business, practitioner, and appointment type. Its `candidate` result means the selected metadata currently appears eligible for online availability reads. It never grants booking, patient disclosure, or staff-request authority.

Every paginated business or relationship list must contain the expected number of records for its `per_page=100` position. A short page with a larger `total_entries` is `unavailable`, even if a later page might make the final count add up. E2E-191 proves such a response cannot be approved and cannot pass a previously approved route's call-time provider recheck.

`ClinikoCatalogueSetup` supplies the host-facing confirmation seam. The host provides an authenticated `HostActor`, account-scoped number routing, a versioned location policy, and a compare-and-swap approval store. The provider-neutral command gateway can list business metadata, inspect one selection, read the stored approval/version, approve, and revoke through this seam. Only a clinic admin for the reader's exact tenant, clinic, and location can do so. Approval requires a single-location route with the expected account, dialed number, and route version; the selected policy version; an eligible Cliniko snapshot no more than 60 seconds old; and a current credential fingerprint. Route and policy are checked before and after the provider reads. Concurrent changes to the approval record fail by version conflict. A read of the stored approval does not itself revalidate current provider eligibility.

An approval stores only clinic configuration: scope, selected Cliniko IDs, route and policy versions, key fingerprint, approver's opaque reference, and timestamps. It fixes both patient action and patient-specific request modes to `unavailable`. This is a clinic administrator's permission to use one read-only availability route. It is separate from Cliniko's API permissions and from a clinic's later approval of any patient-specific staff workflow. `readApprovedRoute` checks the stored approval, exact number route, policy version, key fingerprint, and revocation version before voice ingress without contacting Cliniko. `resolveForCall` additionally rechecks provider eligibility before using the selected catalogue. These reads are sequential, so they cannot guarantee that Cliniko will not change after the final check. The availability reader checks the current online-booking flags before speaking times and preserves a truthful direct-contact fallback if they change. Available times remain provisional.

The availability reader also requires the selected appointment type to remain in the business's current `appointment_type_ids` list. A null, absent, or removed selection cannot produce a time claim, even when `/available_times` would return rows. [Cliniko's business API](https://docs.api.cliniko.com/openapi/business) documents this nullable list; `E2E-193` covers removal after route approval through the signed synthetic runner.

`MemoryClinikoApprovalStore` is a reference adapter and loses approvals on restart. `PostgresClinikoApprovalStore` keeps an append-only, clinic-scoped approval/revocation history with scalar, constrained configuration fields and transactional compare-and-swap. It stores neither the API key nor patient content. The standalone voice runner now reads that PostgreSQL approval at signed webhook admission and call binding. Missing, changed, or revoked approval rejects the next call before a Cliniko read; an already active call retains its captured policy. A production host still needs an authenticated clinic identity source and must use the host-facing confirmation flow before real deployment. The current synthetic test actor and seeded approval do not establish a real clinic's consent. A bounded read-only demo-account check of the catalogue passed (C-LIVE-23), returning an unavailable selection because online booking was disabled. A real clinic must still confirm its own selection and caller wording. The current configuration archive and buyer cutover do not transfer these approval records.
