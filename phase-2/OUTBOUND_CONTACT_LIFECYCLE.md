# Pending outbound contact admission

This is an optional composed launch profile, not outbound activation. Ordinary legacy conditional launches retain their existing v3 shape and grants. A guarded clinic must use this profile for every campaign and location; running a legacy or independent producer is not protected by this hold.

The clinic's current, complete contact-account approval supplies an independently random `contactGuardRef`. Preserve it across campaigns, locations, policy/credential/source-role/runtime changes and restore/remapping. Creating a fresh UUID is not a way to clear unresolved calls. Producer/restore admission must qualify the complete existing opaque allocation history and clinic-wide identity; neither a new database nor missing local rows proves clearance. Native contact history remains authoritative for consent and recorded stops. Current coverage, independent source definitions, broad/private/head/reconsent/exact-number-resolution grants and the existing bounded full scan remain required. Unknown, incomplete, malformed, oversized or quota-denied evidence refuses dispatch.

The owner composes the actual native number-stop reader using its captured contact source and the same physical native180 budget. It checks this evidence at every repeated preparation, including the final provider fence. It retains each granted private query only in invocation-local volatile memory and rechecks current permission synchronously. Independently cleared same-number heads must remain within their exact native effective window after every later wait and immediately before dispatch; the current patient's consent alone cannot cover another patient's old stop. A clinic-account method or source-object replacement cannot silently switch the approved source.

One independent pending-contact allocation is acquired clinic-wide before the ordinary per-campaign call allocation and permanent effect claims. It uses the existing portable opaque allocation storage under domain `abby.outbound-contact-guard.v1`, distinct from `abby.outbound-capacity.v1`. No telephone, telephone hash, patient/native/provider identifier, private context digest, callback token or retry body is written into local allocation rows. Existing atomic tenant locking, full held/released history, origin carryover, export/import and missing-imported-row refusal apply without a schema change. Scope is separately checked; the guard binding itself survives remapping.

A possible-attempt v4 native note retains the guard UUID, distinct contact-allocation UUID and distinct preallocated future contact-outcome action UUID, alongside the older regular-capacity and DNC recovery references. These are binding identities only, not contact completion, native DNC retention, patient verification or a call grant. Lossless digest/recall-ID packing preserves the original1000/1050 summary/note limits. V1–v3 exact persisted bytes and digests remain readable and unchanged. Known no-provider-invocation failure may release this process's acquired holds; permanent effect exclusions never clear. Once the provider method is invoked, response loss, permission withdrawal, abort, deadline or process loss leaves the contact hold intact.

Normal terminal recovery can release the regular call place but cannot release the distinct contact hold. No timer, heartbeat, PID absence, apparent quiet period, patient-phone change, call-terminal response or arbitrary caller-supplied stop status clears pending contact. This patch deliberately supplies no post-dispatch contact-settlement release. Consequently one accepted or unknown call can block the clinic's subsequent guarded launches until a separately qualified native contact-outcome/recovery owner is implemented and approved; this is unfinished engineering, not production throughput or operational readiness.
