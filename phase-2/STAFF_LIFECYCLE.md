# Host-confirmed staff task lifecycle, version 0.1

An opened task may be acknowledged, resolved, or reassigned to the call policy's approved staff destination or operator queue, including after the voice call ends. `StaffWork.planStaffChange` validates the canonical item, host task reference, expected call version, actor reference, current status, and destination. It commits one keyed `staffChange` outbox intent with the item in a pending state. The effect worker marks possible send before calling the optional `StaffLifecycleHost.advanceTask` port. Only a matching `applied` receipt changes the task's canonical status or destination. A rejected result leaves the prior host status visible and requires operator review.

A lost response or expired possible send creates a distinct `staffChangeReconcile` intent under the original command key. `exactApplied` advances the item; `definitiveNonApplied` leaves the prior status and operator-review flag; `stillUnknown` keeps the command pending and visible. No uncertain change is resent. The reference host stores a keyed transition receipt, checks the original task, status, scope, and destination, and can prove the exact result. A production host must also authenticate and authorize the actor and provide authoritative key lookup before advertising this capability.

`staff.change.v1` is discoverable to staff and clinic administrators only when both lifecycle host operations are present. It uses the same command in the direct `lit-html` dashboard. Agents can inspect the redacted queue but cannot mutate it. The dashboard receives a redacted result and refreshes the queue; a stale call version produces a conflict. The standalone server is a local reference with an actor bound by its caller, so deployment must supply authentication.

Memory, PostgreSQL, and browser journeys cover acknowledgment, reassignment, resolution, stale versions, keyed replay, a lost response, process recovery, and unknown outcomes. PostgreSQL proves that the canonical call, effect outbox, and staff-item projection advance together. This does not prove Cliniko task support, an external operator queue, or overdue and delivery-failure alerts. These remain readiness gates for live clinics.
