# Agent command contracts, version 0.1

`CommandGateway.listPermitted()` now returns a permission-filtered catalogue with a stable capability ID, versioned JSON Schema input and result contracts, bound-actor location scope, authority, side-effect class, preconditions, and caller-confirmation requirement. The schemas are self-contained and use a deliberately small JSON Schema subset. The gateway validates untrusted command shape before dispatch and checks the returned `Result` against the advertised result schema. Domain rules such as host evidence, caller affirmation, version conflicts, and tenant scope still run in the owning modules.

An invalid input returns `invalid` without dispatch. An unexpected host exception returns `commandOutcomeUnknown`; a result that violates its published schema returns `responseContractViolation`. Either may follow a committed command, so clients must inspect the relevant policy or call record before considering another mutation. The runtime never treats a schema check as authority to confirm an appointment.

The `booking.propose.v2`, `knowledge.answer.v2`, and `availability.read.v2` commands return a `CallCommandProgress` receipt instead of the internal `CallState` returned by their earlier `v1` contracts. The `v1` commands are no longer advertised or accepted. The receipt includes the submitted turn ID as a trace key, the current call version, action and task keys with statuses, the current pending presentation reference, approved knowledge source references for that turn, and a count/status for that turn's availability. A replay of a turn reports current action and task statuses under its original trace key. It excludes patient and offer records, caller text, approved speech, exact available times, host mutations, and effect payloads. The voice session and presentation dispatcher remain responsible for speaking approved content; an agent command cannot mark playback complete or affirm for a caller.

The clinic-admin-only `clinic.availability.*.v1` commands expose a provider-neutral setup port. An admin can list business metadata, inspect one candidate, read the stored approval and version including its business time zone, approve one read-only route, or revoke it using compare-and-swap. A stored approval is a configuration record, not a live eligibility claim: the call path must recheck routing, policy, and provider eligibility. Credential denial and provider rate limits have distinct typed failures. These commands grant no booking, patient disclosure, or patient-specific staff handoff.

An embedded host with a scoped `StaffQueue` also advertises read-only `staff.health.v1`. It scans at most 5,000 validated queue items and returns only status, overdue, review, pending-change and alert-state counts; no call ID, task key, destination or patient content is returned. The result declares `nonAtomicScan`, because items can change between pages. A larger queue fails with a typed storage error instead of presenting a partial total as complete. The standalone Cliniko composition has no durable staff queue and does not advertise this command by default.

The standalone dashboard still uses the same gateway and its capability endpoint publishes the permitted schemas needed by the browser. The endpoint omits the booking proposal command because the dashboard does not expose that action. Embedded hosts can mount the in-process catalogue without an Abby server. The host must authenticate and bind the actor before constructing the gateway; a self-declared `HostActor` is not an authentication mechanism. A production authenticated admin identity source and a deployed admin workflow for these setup commands remain open.

Embedded and PostgreSQL journeys exercise catalogue discovery, malformed input rejection before host reads, proposal receipt validation, role filtering, tenant isolation, caller confirmation, and absence of patient or spoken content. A browser journey checks schema publication without exposing location identifiers.

`E2E-222` runs one booking script through `CommandGateway` and `TextReception` with two actual storage modes. The standalone adapter uses a call-local `MemoryLedger`, minimal PostgreSQL policy and `DisabledStandaloneHost`; the authorized embedded adapter uses a PostgreSQL call ledger, rich policy and booking host. The same malformed, role-denied and foreign-scope commands fail in both. A booking setting change does not enable standalone patient action. The embedded action needs played details and caller affirmation, then is stopped by the shared write-stop rule on a later call. The standalone database and backup contain no patient or call canaries; the embedded call ledger can recover actions after reconnecting. This proves the text/core seam. E2E-222 also runs signed HTTP/WebSocket booking through both voice compositions: standalone speaks the unavailable fallback and closes on an unsupported affirmation, while embedded waits for the detail playback mark and caller affirmation before one booking. A third signed embedded case applies the typed clinic stop after the detail mark, hears an unresolved notice with no booking, resumes writes without replay, and recovers the unsupported action after reconnect. Its strict standalone database and backup stay clear of private canaries. Signed admin command authorization, other agent commands and a real buyer identity/storage integration remain separate conformance work.

`E2E-223` extends that cross-mode seam to knowledge and call review. Both modes give a truthful fallback before approval. Strict standalone denies knowledge drafts and call review and persists no call or knowledge canary. The embedded reference mode permits a clinic admin to draft and approve, then gives a new call a sourced answer. An agent cannot approve or read caller and answer text through review; foreign-scope review is denied. Authorized redacted review survives a new database connection. A shared signed synthetic call script now tests fallback before approval in both modes and approved speech only in a later embedded call, plus standalone database and backup privacy and embedded redacted recovery. Agent permission and review-command checks remain at the text/core seam; buyer-host integration is open.
