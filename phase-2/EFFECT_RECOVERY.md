# Durable effect recovery, version 0.1

The ledger exposes a bounded, scoped `findRecoverableEffects` scan. It returns pending outbox effects and possibly-sent effects only after the 60-second recovery delay. PostgreSQL reads the indexed outbox joined to its owning call and uses database time; the embedded memory ledger implements the same contract. Pages contain at most 100 effect IDs. `EffectRecovery` scans from a cursor and wraps after the end, processes effects for one call in order, and processes up to four different calls concurrently.

A pending effect goes through the normal `EffectWorker` and its durable possible-send barrier. An aged possibly-sent booking write, staff-task opening, staff change, or [operator alert](OPERATOR_ALERTS.md) goes through its matching recovery transition. That transition creates a separate exact-key reconciliation intent; recovery never calls the original mutation again. The next scan performs the host read and applies a typed result. Host lookup failures leave pending work intact and appear in the recovery report.

Each effect dispatcher claims a scoped call lease before processing that call's effects. This covers recovery workers, the foreground text/voice drain, and immediate staff-change dispatch. The PostgreSQL claim is atomic across processes, uses database time, expires after 60 seconds, and renews every 15 seconds while work runs. The memory adapter follows the same owner-token rules. A busy recovery call is deferred to a later scan; a busy foreground drain returns the current persisted state, leaving work for recovery. A crashed worker leaves a lease that can be reclaimed after expiry; a stale owner cannot renew or release a successor's claim. Lease loss aborts the worker's current host call. Durable possible-send barriers and exact-key reconciliation remain necessary because lease expiry cannot undo a remote request already sent. Direct uses of `EffectWorker` outside these compositions must acquire the same lease before dispatch.

Migration `010_effect_call_lease_versions` keeps a monotonically increasing version on each call's lease row, including after release. The composed workers pass the claimed owner and version into every effect transition. Memory checks the guard before applying the reducer; PostgreSQL locks the call and lease rows, checks owner, version, and expiry against database time, then commits the state, event, outbox, and staff projection in one transaction. A stale or forged version returns `leaseLost` without advancing the call. This fences a late effect result after another owner reclaims the call, including when the same owner name is reused. The lower-level `CallRuntime` still permits unguarded transitions for controlled fixtures and non-effect callers; deployment code must use the composed dispatch paths or supply a guard to any direct effect worker.

Host calls now have a bounded worker deadline (15 seconds by default, configurable for a deployment or test) and receive an `AbortSignal`. A timeout after a host write, staff opening, staff change, or operator alert has crossed its durable possible-send barrier becomes **uncertain** and follows that effect's exact-key reconciliation path. A timed-out read-only reconciliation leaves its intent pending, so the next recovery tick can retry the read without replaying the mutation. A timed-out knowledge read becomes unavailable. The worker's deadline frees the recovery tick even if a host adapter ignores the signal; adapters should also cancel their own network work because a late remote effect may still complete. A host must not report definitive noncommit while its timed-out request could still commit. A late write response alone never changes an uncertain action to committed.

`EffectWorkLoop` runs the scan immediately on host startup, then periodically without a live voice session. It coalesces overlapping ticks and stops cleanly. The local dashboard demo starts it with the reference host; an embedded monolith or standalone deployment must start the loop with its own scoped host lookup and operational reporting. This is a recovery mechanism, not evidence that Cliniko supports exact write reconciliation or staff tasks. The standalone default keeps booking, cancellation, rescheduling, and intake unavailable until a host-owned command and task path is proven; synthetic request-only tests do not authorize storing patient-specific staff work in Abby.

Memory and PostgreSQL journeys cover pending work, tenant isolation, a possibly-sent booking write, crashed staff-task opening and resolution, unavailable host lookup, bounded pagination, lease contention across foreground and recovery paths, lease expiry, rejected stale result versions, and no mutation replay. Text E2E cases also cover timed-out writes, stalled reconciliation ticks, aborted host signals, late responses, and timed-out staff opening. A timer test covers startup, overlap, and shutdown. The existing browser suite checks the staff-facing results.
