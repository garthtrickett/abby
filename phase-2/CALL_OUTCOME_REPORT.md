# Scoped call outcome report, version 0.1

`CallOutcomeReport` reads bounded pages of call aggregates through `LedgerStore.listCalls` and returns only call IDs, lifecycle, and outcome counts. The PostgreSQL adapter queries a clinic-scoped index; the reference ledger uses the same cursor contract. Pages contain at most 100 calls and are ordered by call ID. The agent-native `calls.outcomes.v1` command and direct `lit-html` dashboard use the same report. The host actor's location scope is applied before any row is returned.

Counts distinguish committed actions from unresolved actions, staff requests from host-confirmed tasks, and failed or review-required staff work. A system-failure count requires an actual `systemFailure` staff item. [Terminal evidence](CALL_TERMINAL_EVIDENCE.md) adds caller disconnect, media failure, lease closure, and connected-transfer counts without labeling any of them as abandonment. A requested task is not described as delivered. Rows omit patient references, spoken text, appointment details, and host payloads. The dashboard labels totals as **loaded calls** because pages can change while the clinic is active; they are not an audited all-time snapshot.

Memory and PostgreSQL journeys cover action and task outcomes, a system-failure fallback, tenant isolation, redaction, and pagination. A browser scenario exercises the staff view and its HTTP command boundary. Caller abandonment still cannot be inferred from a hangup alone. Abandonment reporting, date-windowed stable snapshots, and release-grade latency/cost analytics remain open parts of FR-15.

The standalone Cliniko runner does not use this patient-linked call report. Its default `PostgresOperationalCounters` store tracks nine fixed-code, clinic-scoped totals: denied signed admission **checks** (a call may cause more than one check), constructed call owners, voice failures, ended calls, local Cliniko budget denials, budget failures, provider 429 responses, provider 5xx and fetch failures during availability reads, and unavailable intent classifications. Budget and intent-classification totals count attempts or responses, not distinct calls. Atomic increments share committed totals across runners and survive restart. Lifetime rows contain only tenant, clinic, location, code and count; they have no call ID, caller number, transcript, event timestamp or patient outcome. An abrupt process death can lose an uncommitted increment, so totals are best effort and cannot reconstruct exact calls or claim that a staff task was delivered. An injected host may instead use the volatile `StandaloneOperationalCounters` port. An owner-only `ABBY_VOICE_OPERATIONS_TOKEN_HEX` enables the exact `GET /internal/operations` endpoint for the runner's configured clinic; `npm run voice:ops` reads it locally without putting the token in command arguments. The endpoint is absent without the token, rejects missing or wrong tokens and non-GET requests, and refuses snapshots with extra fields or invalid counts. The token is an operator process credential, not a clinic identity/role source. Synthetic signed admission, speech-failure, provider-429, provider-unavailable, cross-process increment and PostgreSQL/backup canary checks cover this boundary; it is one slice of D3's aggregate operations contract.

`GET /internal/operations/daily` uses that same exact owner token and returns seven consecutive UTC calendar dates with all nine counts, including zero-filled days. `npm run voice:ops -- --daily` reads and validates this view. A committed PostgreSQL record increments both the lifetime total and the daily row atomically; the daily table stores only tenant, clinic, location, UTC date, fixed code and count. Active writes and daily reads prune old rows for their own clinic scope. Runner startup and periodic cleanup remove old rows across idle clinics while a runner is active; the [independent retention timer template](../deploy/voice/OPS_RETENTION_SCHEDULE.md) is available for cleanup when every runner is stopped, but must be installed and monitored by the deployer. E2E-217 checks signed-call output, denied access, malformed snapshots, cross-process atomicity, UTC rollover, scope isolation and canary exclusion. Counts remain best effort and are never patient outcome reconstruction.

The standalone runner also prunes expired daily rows across all clinic scopes before opening its listener and every six hours while it remains up. `npm run voice:ops:prune` runs the same cleanup once from a separate owner process using `DATABASE_URL`; it prints no scope, patient or credential values. A deployable systemd service/timer template runs that command at midnight UTC independently of the voice process. The units are rendered and locally validated, not installed or activated here; a host or database outage can still delay expiry. E2E-218 proves startup cleanup of an idle clinic, the one-shot command, preservation of lifetime totals and the boundary between scoped reads and global expiry. Neither cleanup path stores a per-call record.

`npm run voice:ops:check` reads today's UTC daily counts directly from PostgreSQL for the owner-configured `ABBY_TENANT_ID`, `ABBY_CLINIC_ID` and `ABBY_LOCATION_ID`. `ABBY_VOICE_OPS_THRESHOLDS_JSON` maps selected fixed codes to positive integer daily thresholds; an omitted code is off. The command emits only `{date, alerts:[{kind,count,threshold}]}` and returns exit status `2` for a crossed threshold, `0` for none or `1` for an unavailable/invalid check. It has no notification transport, delivery receipt or deduplication guarantee; an operator scheduler must decide how to deliver and acknowledge that signal. E2E-219 covers an enabled threshold, a higher clear threshold, foreign-scope isolation and invalid configuration without exposing patient or credential values.

`npm run voice:ops:send` adds a separate owner-run transport for retained crossings across seven UTC days. The configured `ABBY_VOICE_ALERT_WEBHOOK_URL` must use HTTPS without URL credentials, query or fragment, and `ABBY_VOICE_ALERT_TOKEN_HEX` is a 64-character owner secret sent only as a bearer header. Each POST has a five-second deadline, refuses redirects, and contains only schema version, UTC date, fixed code, count, threshold and a stable HMAC retry key specific to that date. A 2xx is receiver acceptance; non-2xx or transport failure returns a fixed error without printing URL, scope, response or secret. Every scheduled run can repeat accepted alerts; the receiver must persist stable-key deduplication for at least seven days. The [systemd timer renderer](../deploy/voice/OPS_ALERT_SCHEDULE.md) supplies a deployable independent 15-minute schedule, but no unit or clinic recipient is installed here, and no human acknowledgment or staff delivery is claimed. E2E-220 proves same-day and prior-day PostgreSQL-to-webhook behavior with a synthetic loopback receiver, a stable per-day retry key and no patient or call content. Crossings older than the seven-day retention window cannot be recovered.

For an authorized embedded host, `staff.health.v1` aggregates the host-owned `StaffQueue` projection into bounded clinic/location counts. It reports requested, open, acknowledged, resolved, review-needed and failed states separately, plus overdue, pending changes, review flags and alert states. Alert-state counts are per alert reason and may exceed task counts. The scan fixes one observation clock but is not an atomic database snapshot; it fails rather than returning incomplete totals beyond 5,000 items. The command output contains no call or task key, destination, patient detail or free text. E2E-221 covers a 51-item page boundary, foreign-tenant isolation, PostgreSQL task projection and redaction. The standalone Cliniko runner has no staff queue; this report does not imply Cliniko follow-up was created or delivered.
