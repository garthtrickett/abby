# Scoped call outcome report, version 0.1

`CallOutcomeReport` reads bounded pages of call aggregates through `LedgerStore.listCalls` and returns only call IDs, lifecycle, and outcome counts. The PostgreSQL adapter queries a clinic-scoped index; the reference ledger uses the same cursor contract. Pages contain at most 100 calls and are ordered by call ID. The agent-native `calls.outcomes.v1` command and direct `lit-html` dashboard use the same report. The host actor's location scope is applied before any row is returned.

Counts distinguish committed actions from unresolved actions, staff requests from host-confirmed tasks, and failed or review-required staff work. A system-failure count requires an actual `systemFailure` staff item. [Terminal evidence](CALL_TERMINAL_EVIDENCE.md) adds caller disconnect, media failure, lease closure, and connected-transfer counts without labeling any of them as abandonment. A requested task is not described as delivered. Rows omit patient references, spoken text, appointment details, and host payloads. The dashboard labels totals as **loaded calls** because pages can change while the clinic is active; they are not an audited all-time snapshot.

Memory and PostgreSQL journeys cover action and task outcomes, a system-failure fallback, tenant isolation, redaction, and pagination. A browser scenario exercises the staff view and its HTTP command boundary. Caller abandonment still cannot be inferred from a hangup alone. Abandonment reporting, date-windowed stable snapshots, and release-grade latency/cost analytics remain open parts of FR-15.

The standalone Cliniko runner does not use this patient-linked call report. Its default `PostgresOperationalCounters` store tracks eight fixed-code, clinic-scoped totals: denied signed admission **checks** (a call may cause more than one check), constructed call owners, voice failures, ended calls, local Cliniko budget denials, budget failures, provider 429 responses, and provider 5xx and fetch failures during availability reads. The budget totals count request attempts or responses, not distinct calls. Atomic increments share committed totals across runners and survive restart. Lifetime rows contain only tenant, clinic, location, code and count; they have no call ID, caller number, transcript, event timestamp or patient outcome. An abrupt process death can lose an uncommitted increment, so totals are best effort and cannot reconstruct exact calls or claim that a staff task was delivered. An injected host may instead use the volatile `StandaloneOperationalCounters` port. An owner-only `ABBY_VOICE_OPERATIONS_TOKEN_HEX` enables the exact `GET /internal/operations` endpoint for the runner's configured clinic; `npm run voice:ops` reads it locally without putting the token in command arguments. The endpoint is absent without the token, rejects missing or wrong tokens and non-GET requests, and refuses snapshots with extra fields or invalid counts. The token is an operator process credential, not a clinic identity/role source. Synthetic signed admission, speech-failure, provider-429, provider-unavailable, cross-process increment and PostgreSQL/backup canary checks cover this boundary; it is one slice of D3's aggregate operations contract.

`GET /internal/operations/daily` uses that same exact owner token and returns seven consecutive UTC calendar dates with all eight counts, including zero-filled days. `npm run voice:ops -- --daily` reads and validates this view. A committed PostgreSQL record increments both the lifetime total and the daily row atomically; the daily table stores only tenant, clinic, location, UTC date, fixed code and count. Active writes and daily reads prune old rows for their own clinic scope. Runner startup and periodic cleanup remove old rows across idle clinics while a runner is active; an independent scheduler is still required for a strict deadline during complete runner downtime. E2E-217 checks signed-call output, denied access, malformed snapshots, cross-process atomicity, UTC rollover, scope isolation and canary exclusion. Counts remain best effort and are never patient outcome reconstruction.

The standalone runner also prunes expired daily rows across all clinic scopes before opening its listener and every six hours while it remains up. `npm run voice:ops:prune` runs the same cleanup once from a separate owner process using `DATABASE_URL`; it prints no scope, patient or credential values. A stopped runner cannot enforce calendar-time deletion by itself, so production deployment needs an independent daily scheduler for that command if it requires a strict retention deadline. E2E-218 proves startup cleanup of an idle clinic, the one-shot command, preservation of lifetime totals and the boundary between scoped reads and global expiry. Neither cleanup path stores a per-call record.

`npm run voice:ops:check` reads today's UTC daily counts directly from PostgreSQL for the owner-configured `ABBY_TENANT_ID`, `ABBY_CLINIC_ID` and `ABBY_LOCATION_ID`. `ABBY_VOICE_OPS_THRESHOLDS_JSON` maps selected fixed codes to positive integer daily thresholds; an omitted code is off. The command emits only `{date, alerts:[{kind,count,threshold}]}` and returns exit status `2` for a crossed threshold, `0` for none or `1` for an unavailable/invalid check. It has no notification transport, delivery receipt or deduplication guarantee; an operator scheduler must decide how to deliver and acknowledge that signal. E2E-219 covers an enabled threshold, a higher clear threshold, foreign-scope isolation and invalid configuration without exposing patient or credential values.
