The reference fixture demonstrates core composition only; it is not a production host or evidence for another provider. Splose stays unverified until account access and probes are available; its API documentation alone cannot establish account behavior. Product approval must assign each profile and capability a final `execute`, `requestOnly`, or `unavailable` mode with the cited evidence and a safe fallback. For standalone Cliniko, `requestOnly` also requires a proven Cliniko-owned durable request and staff route; without one, use `unavailable` and the approved caller fallback. A known unsupported or unsafe mutation never inherits execute mode from another provider.

## Operation-specific activation contract — 2026-10-03

[The Cliniko write activation contract](../phase-2/CLINIKO_WRITE_ACTIVATION.md) records all five operations separately, starting with cancellation. Current standalone modes remain unavailable. E2E-264 uses actual edges with a synthetic provider to expose the target-change window and independent cancellation sends, same-slot creates, conflicting in-place moves, concurrent patient creation and duplicate recall markers. Its whole cancellation call preserves uncertain status, truthful pending-review speech and no replay. These are local counterexamples, not new live Cliniko claims or proof that an atomic primitive is impossible. The checked published API does not establish the required conditional-target, reservation-consumption or idempotency guarantees; provider/owning-host evidence remains necessary. The contract names acceptable protection, storage/owner requirements, rejection of insufficient alternatives and exact release proof for every operation.

### Owning-host appointment commit proof

The [owning-host write design](../phase-2/OWNING_HOST_WRITE_DESIGN.md) and E2E-265 provide a concrete native PostgreSQL mechanism for protected cancellation, non-overlapping booking and in-place rescheduling when an authorized buyer owns all diary mutation paths. It uses disposable synthetic host records; there is no new Abby migration or standalone storage allowance. This is a database design proof, not a runnable clinical host or evidence of Cliniko atomic writes. Actual adapter, caller/policy, recovery/work ownership and voice release gates remain open; all standalone writes remain unavailable.
