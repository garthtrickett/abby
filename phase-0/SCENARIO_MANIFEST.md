# Scenario manifest, version 0.1

[SCENARIO_MANIFEST.json](SCENARIO_MANIFEST.json) tracks the 125 stable E2E IDs in [Technical Design Section 11](../TECHNICAL_DESIGN.md#11-verification-design). Each row retains its requirement mapping and required journey, names a distinct planned fixture and fixture family, and records intended compositions and earliest implementation phase. The capability and setting maps cover the current agent catalogue and its three behavior settings. `test/contract/scenario-manifest.test.ts` checks the design and catalogue for drift, duplicate or missing IDs, and test-file references.

Every `fullCallEvidence` entry is **planned**. Existing text, browser, provider-contract, and synthetic voice tests are valuable evidence, but none proves the complete full-call scenario with the required production entry point and transport observations. `E2E-125` records passing **text-only** evidence from the standalone Cliniko availability journey; it remains planned for full-call evidence. `fixture.state` describes only the named fixture's current implementation level, not release approval.

Before P0-09 can close, each planned fixture needs explicit inputs and observed caller, host, ledger, and staff assertions; independently triggerable failures need separate fixtures. Typed failure kinds still need scenario mappings. The first Phase 1 slice must add real full-call test files and change their manifest entries in the same pull request, while clinic and provider gates remain governed by the support matrix. A new feature or setting must add or extend its E2E ID and test at the same time; this registry alone does not make an untested feature releasable.
