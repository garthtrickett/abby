# Scenario manifest, version 1.1

[SCENARIO_MANIFEST.json](SCENARIO_MANIFEST.json) tracks the 191 stable E2E IDs in [Technical Design Section 11](../TECHNICAL_DESIGN.md#11-verification-design). The design table owns each journey's wording; the registry adds its requirement mapping, fixture family, intended compositions, earliest implementation phase, and evidence status. Each scenario's fixture ID is `fixture-` plus its lowercase E2E ID. The capability and setting maps cover the current agent catalogue and its three behavior settings. `test/contract/scenario-manifest.test.ts` checks the design and catalogue for drift, duplicate or missing IDs, and test-file references.

Every `fullCallEvidence` entry is **planned**. E2E-018 now has signed synthetic voice evidence for automation default, enabled, disabled, invalid-value, active-call snapshot, and failed-readiness paths in both the reference host and the strict PostgreSQL-backed standalone transient composition. The standalone fixture uses no Cliniko read; it checks exact caller wording and absent call, effect, and staff rows in its database and backup. It does not establish production HTTP/WSS runner behavior or full-call carrier evidence.

They remain synthetic voice evidence; actual Twilio fallback ringing is unproven.

The embedded fixture keeps its call state in host memory; the standalone fixture scans its isolated database and backup. This is text and architecture evidence, not a full voice call or an actual buyer monolith integration.

E2E-190 runs a signed local keypad call against an incomplete Cliniko available-time page. The adapter refuses the short page, and the standalone runner speaks the generic unavailable fallback without an appointment write or patient-data persistence. Carrier behavior remains unverified.

E2E-191 checks that an incomplete Cliniko relationship page cannot produce a new clinic approval or pass the provider recheck for an existing approval. It uses a synthetic catalogue and host admin; production clinic identity and selection remain open.

Before P0-09 can close, each planned fixture needs explicit inputs and observed caller, host, ledger, and staff assertions; independently triggerable failures need separate fixtures. Typed failure kinds still need scenario mappings. The first Phase 1 slice must add real full-call test files and change their manifest entries in the same pull request, while clinic and provider gates remain governed by the support matrix. A new feature or setting must add or extend its E2E ID and test at the same time; this registry alone does not make an untested feature releasable.
