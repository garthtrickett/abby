# Scenario manifest, version 1.5

[SCENARIO_MANIFEST.json](SCENARIO_MANIFEST.json) tracks the 204 stable E2E IDs in [Technical Design Section 11](../TECHNICAL_DESIGN.md#11-verification-design). The design table owns each journey's wording; the registry adds its requirement mapping, fixture family, intended compositions, earliest implementation phase, and evidence status. Each scenario's fixture ID is `fixture-` plus its lowercase E2E ID. The capability and setting maps cover the current agent catalogue and its behavior settings. `test/contract/scenario-manifest.test.ts` checks the design and catalogue for drift, duplicate or missing IDs, and test-file references.

Every `fullCallEvidence` entry is **planned**. Before P0-09 can close, each planned fixture needs explicit inputs and observed caller, host, ledger, and staff assertions; independently triggerable failures need separate fixtures. Typed failure kinds still need scenario mappings. The first Phase 1 slice must add real full-call test files and change their manifest entries in the same pull request, while clinic and provider gates remain governed by the support matrix. A new feature or setting must add or extend its E2E ID and test at the same time; this registry alone does not make an untested feature releasable.
