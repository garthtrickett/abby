# No-number P0/P1 gap trace

[The versioned trace](NO_NUMBER_GAP_TRACE.json) assigns each P0/P1 row in the [core and Cliniko comparison](../KAREN_ABBY_CORE_CLINIKO_GAP_ANALYSIS.md) a stable `CORE-*` or `CLINIKO-*` ID. Each row has three derived case IDs, ending `-P` for a positive path, `-N` for a denied or ineligible path, and `-F` for an independently triggered failure. The three semicolon-separated fixture clauses are in that same order. All clauses inherit the patient-free tenant, clinic, location and caller in `fixtureBase`; a clause overrides only what it names. [The case contracts](NO_NUMBER_CASE_CONTRACTS.json) add caller intent, applicable policy, allowed spoken claim, host effect, fallback, and a privacy assertion for each case. Its columns apply in the declared order. Eight additional `NN-EDGE-*` cases explicitly cover anonymous and stale callers, on-behalf requests, shared-number location choice, withdrawal, urgent language, interruption, and hangup during a possible write. These are versioned inputs and expected outcomes, not a record of test results.

Each case points to the nearest existing `E2E-*` design scenario. Consult [the scenario manifest](SCENARIO_MANIFEST.json) for the current implementation level and evidence file. A reference-host or synthetic voice scenario must not be read as proof of a standalone Cliniko capability. The `gate` says what remains before the corresponding product gap can close. A newly discovered P0/P1 gap must be added to this trace and given a fixture and scenario mapping; `test/contract/no-number-gap-trace.test.ts` checks that rule against the comparison table.

The A1 **ledger** exit is met: 28 P0/P1 gaps have 84 triad cases plus eight explicit edge cases with versioned inputs and expected outcomes, and every row names its missing activation or proof gate. Implementation is separate. A case becomes implemented only when its inputs and assertions are explicit in an executable test and the scenario manifest points to passing evidence. It becomes full-call evidence only under the manifest's separate full-call contract. The mapped scenarios include planned and reference-only cases; no capability is promoted by this ledger.

For `CORE-01-N`, E2E-054 now checks provider-account separation and ambiguous routing in memory and PostgreSQL, and signed local HTTP refusal of an unlisted dialed number or mismatched account before call-owner construction. This is synthetic route isolation; owned-number carrier behavior remains the `CORE-01` gate.
