# No-number P0/P1 gap trace

[The versioned trace](NO_NUMBER_GAP_TRACE.json) assigns each P0/P1 row in the [core and Cliniko comparison](../AEVA_ABBY_CORE_CLINIKO_GAP_ANALYSIS.md) a stable `CORE-*` or `CLINIKO-*` ID. Each row has three derived case IDs, ending `-P` for a positive path, `-N` for a denied or ineligible path, and `-F` for an independently triggered failure. The three semicolon-separated fixture clauses are in that same order. All clauses inherit the patient-free tenant, clinic, location, caller, policy, and privacy invariant in `fixtureBase`; a clause overrides only what it names. These are candidate inputs for executable cases, not a record of test results.

Each case points to the nearest existing `E2E-*` design scenario. Consult [the scenario manifest](SCENARIO_MANIFEST.json) for the current implementation level and evidence file. A reference-host or synthetic voice scenario must not be read as proof of a standalone Cliniko capability. The `gate` says what remains before the corresponding product gap can close. A newly discovered P0/P1 gap must be added to this trace and given a fixture and scenario mapping; `test/contract/no-number-gap-trace.test.ts` checks that rule against the comparison table.

This first trace deliberately does **not** complete work package A1: the existing design scenarios do not yet give each derived case its own expected spoken claim, host effect, fallback, and case-level privacy observation. Those assertions belong in executable text and synthetic voice journeys as the related capability is built. A case becomes implemented only when its inputs and assertions are explicit in a test file and the scenario manifest points to that passing evidence. It becomes full-call evidence only under the manifest's separate full-call contract. This prevents a planning row from being promoted by documentation alone.
