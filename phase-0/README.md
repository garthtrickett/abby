The Cliniko [read-only probe](probes/cliniko_readonly.py) prompts for its key in a terminal. Credentials and provider response records are not committed. A 200 GET proves only that this key can perform that read; it does not prove safe automation or write permission.

`C-LIVE-17` in `test/live/cliniko-rehearsal.test.ts` is an opt-in demo-account E2E. It creates one marked synthetic patient with a phone number, runs the guarded production phone-index refresh into a disposable PostgreSQL database, checks the live candidate re-read, and drives the standalone text availability path through the real Cliniko adapter. It temporarily enables the demo business's online-booking flag when needed, then verifies that the patient is archived and the original flag restored. It scans the disposable database and in-memory backup dump for synthetic names, email, caller text, and returned time canaries; patient phone and ID are checked only in the allowed index. The test prints no provider records or identifiers. Run it only against the sanctioned demo account, separately from other account probes:

```sh
work run "Abby live Cliniko rehearsal" -- bash scripts/with-postgres.sh env ABBY_LIVE_CLINIKO_EVAL=1 node --env-file=/absolute/path/to/owner-only.env --test test/live/cliniko-rehearsal.test.ts
work wait "Abby live Cliniko rehearsal"
```

The test requires `ABBY_CLINIKO_API_KEY` and `ABBY_CLINIKO_CONTACT_EMAIL` in that file. A failed or killed process can leave a synthetic patient or changed demo setting; inspect and reconcile the demo account before another write probe if cleanup was not verified. A passing run does not approve caller identity, booking, patient-specific handoff, production backups, or live telephony.

## Local text availability entrypoint

`npm run text:availability` accepts one JSON request on stdin: `{"text":"Do you have an opening?","from":"2026-10-02","to":"2026-10-02"}`. It requires `DATABASE_URL`, `ABBY_TENANT_ID`, `ABBY_CLINIC_ID`, `ABBY_LOCATION_ID`, `ABBY_CLINIKO_API_KEY`, `ABBY_CLINIKO_CONTACT_EMAIL`, `ABBY_CLINIKO_BUSINESS_ID`, `ABBY_CLINIKO_PRACTITIONER_ID`, and `ABBY_CLINIKO_APPOINTMENT_TYPE_ID` in the environment. Use a dedicated, freshly migrated standalone database: a startup preflight refuses known rich reference call, event, setting, knowledge, voice-lease, and work rows before it reads a caller question or contacts Cliniko. The response is one JSON line with an availability status and transient message. The command writes no caller text, patient details, appointment IDs, or offered times to Abby's database. It accepts at most 8 KiB of input and a seven-day date span. It is a local text probe; stdout acceptance is recorded as text presentation, not proof the caller read it. Booking, appointment disclosure or changes, and patient-specific staff handoff remain disabled. The latter requires the clinic approval and workflow proof in [D-07](DECISIONS.md).

`npm run demo:availability-console` serves the same strict runner through a standalone lit-html page on `127.0.0.1:3401` (override with `ABBY_AVAILABILITY_PORT`). It uses the same environment variables and startup preflight. The HTTP route accepts only a question and a seven-day date range; the browser clears the question after each result, and every response has `Cache-Control: no-store`. This is a local text probe for provisional availability, with no authentication or live patient-traffic approval. E2E-125 has a browser journey and a PostgreSQL HTTP journey that checks database, disposable-backup, and configuration-archive canaries after text completion. Patient-specific handoff stays disabled until a clinic approves and proves the D-07 workflow.
