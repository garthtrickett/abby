# Cliniko phone index and patient-data boundary

**Status:** Phone-index storage, synthetic full scan, page-checkpointed refresh, periodic refresh worker, and live candidate recheck are implemented and locally tested. The full receptionist flow is not yet compliant. This contract supersedes earlier proposals for retained transcripts, recordings, patient-specific presentation text, action payloads, and patient-linked call history in Abby.

## Storage rule

The only patient information Abby may persist is a Cliniko patient ID and a patient phone number. The allowed relation is `(tenant, clinic, normalizedPhone, clinikoPatientId)`. A phone can map to multiple patient IDs, and one patient can have multiple phones. Tenant and clinic are routing scope, not evidence of caller identity. The index has no name, date of birth, email, appointment, call ID, outcome, note, recording, transcript, or free-text column. No derived hash, ciphertext, trace, error, cache, backup, archive, or log may carry a prohibited patient value. Phone numbers and IDs have explicit deletion and rebuild paths. Generic clinic knowledge and settings must be checked for patient-specific content before persistence.

The call path receives the authenticated transport's presented caller number. The connected voice call exposes a transient candidate lookup only after its clinic location is bound; the number is not copied into its durable admission, call state, or event payload. It normalizes the number with the clinic's configured country/number plan and queries the local index for that clinic. Unparseable, withheld, or ambiguous numbers yield no automatic patient selection. Candidate IDs are re-read from Cliniko at call time and accepted as candidates only if the returned, non-archived record still has the presented phone. The re-read data stays transient. A caller ID match is never identity verification; a shared number must not disclose one patient's appointment to another caller. Clinic-approved verification and exact host authorization are still required before appointment reads or writes.

## Sync and freshness

[Cliniko's patient API](https://docs.api.cliniko.com/openapi/patient) documents `patient_phone_numbers` in patient records but does not list phone among the `GET /patients` filters. The adapter must page through patient records outside the call path, extracting only `id` and `patient_phone_numbers` into a staged clinic-scoped index. It discards every other response field immediately. A complete scan atomically replaces the published generation; partial pages are never published. The resumable checkpoint stores page position, expected generation, counters, seen patient IDs, and phone-to-ID links; no other patient fields enter it. Malformed records, detected source changes, and oversized snapshots discard the checkpoint and fail closed. Temporary provider failures retain complete pages for retry and mark the published generation stale. A process killed mid-scan cannot mark the generation stale immediately; the ordinary freshness window still expires it. The rate budget respects Cliniko's response headers and bounded retries. Incremental `updated_at` reads may reduce lag, but periodic full reconciliation is required to catch removals, archives, merges, and changed numbers. No live call starts a whole-clinic scan.

The published generation records completion time, source scope, country calling code, and normalization version separately from the phone/ID rows. A generation produced before this metadata existed is stale until rebuilt. Readiness requires a complete generation under the current normalization plan and within an approved freshness window. A country-code or algorithm-version change blocks candidate lookup immediately and makes the refresh worker rebuild the clinic index even if its previous completion time is recent. A stale or missing generation blocks automatic patient lookup and routes to bounded clarification or staff. Even a fresh generation supplies candidates only: the live Cliniko read rejects stale phone links and archived records. After the Cliniko reads, candidate lookup checks the same local generation and link set again; a concurrent disconnect, stale mark, or replacement returns no IDs. If Cliniko is unavailable, Abby does not infer a patient from the local index alone. Disconnect atomically removes published and staged links and records a clinic-scoped disabled flag. It retains only a stale, non-patient generation counter so a reconnect cannot reuse an in-flight lookup's generation. A still-running or restarted worker cannot recreate links while the flag is disabled; reconnect requires an explicit `enable` operation after clinic ownership and credentials are established again.

The standalone `npm run phone-index:refresh` worker takes `DATABASE_URL`, `ABBY_TENANT_ID`, `ABBY_CLINIKO_API_KEY`, `ABBY_CLINIKO_CONTACT_EMAIL`, and `ABBY_COUNTRY_CALLING_CODE` from its environment, plus `ABBY_CLINIC_ID` to scope one clinic. Optional `ABBY_PHONE_REFRESH_EVERY_MS` and `ABBY_PHONE_REFRESH_POLL_MS` control the interval. It scans at startup when no fresh generation exists, then polls for due refreshes; results log only `fresh`, `refreshed`, `busy`, `disabled`, or `failed`. Before a due scan, a separate PostgreSQL session claims a clinic-scoped advisory lock; another worker reports `busy` without reading Cliniko and retries on its next tick. The lock releases after success or failure, and PostgreSQL releases it if the owner process dies. After taking the lock the worker rechecks freshness to avoid a redundant scan. The scan resumes the same page after a local budget reset or provider 429, with at most twelve bounded waits. After a process restart, it resumes at the next uncommitted page when the checkpoint is less than 24 hours old, the country code is unchanged, and the published generation has not changed. Each complete page commits atomically; publication requires every expected page. It accepts up to 100,000 patient records and 100,000 unique phone-to-ID links; larger snapshots fail closed. A failed scan marks its starting generation stale while preserving published rows; a newer concurrent publication remains fresh, and an older scan cannot replace it. A lost lock connection can allow overlapping reads until page/generation fences reject an obsolete writer; stronger owner fencing and detection of Cliniko changes during a long scan remain required before large-clinic readiness.

Normalization must be deterministic and conservative. The current plan is version 1 plus the clinic's configured country calling code. Bump the version when the normalization algorithm changes so old generations cannot be reused. Preserve a canonical international representation and reject numbers that cannot be unambiguously normalized. Do not match by suffix, strip arbitrary leading digits, or collapse extensions into a patient phone. Only documented patient phone fields enter the index; fax and other non-calling numbers require an explicit product rule before matching. A fixture covers Australian local and international forms, shared family numbers, missing caller ID, extensions, changed numbers, archive, two clinics with the same number, and a country-code change.

## Durable action boundary

Patient and appointment details needed for a live call may exist in process memory but not Abby persistence. In a standalone Cliniko clinic, Cliniko alone must own the durable patient-specific request, appointment target or offer, exact-key reconciliation, staff follow-up, and review status. An embedded buyer can supply its own authorized patient/work system through the same core seams. Abby may hold a random, non-reversible command reference only while it cannot expose a patient-linked outcome through that reference or its surrounding call metadata. The storage serializer is an explicit allowlist and rejects unexpected fields. If Cliniko cannot own and safely reconcile the patient-specific operation or staff request, the corresponding standalone capability is unavailable, including `requestOnly`; Abby may provide an approved caller fallback and a non-patient operational alert, without claiming staff received a task or a booking was submitted.

Before any real patient traffic, an E2E test must drive a phone-index refresh, candidate lookup, shared-number verification failure, live Cliniko re-read, patient-specific action, retry/crash, staff handoff, call review, export, logs, and backup fixture. It scans every Abby durable surface for canary names, dates, appointment IDs/times, request text, and patient-linked outcomes. Every new feature or setting toggle extends that E2E with its new persistence path. A test that merely checks a redacted UI is insufficient. `test/storage/standalone-privacy-journey.test.ts` now covers one connected text-only slice: staged phone refresh, shared-number live re-read, booking and appointment fallback, the setting toggle, configuration export before a call, export rejection after a call, call reload, database-wide canary scan, and phone-index disconnect deletion. This does not satisfy the real-traffic gate: approved caller verification, enabled patient actions and staff handoff, retry/crash, logs, and a backup fixture remain unproven. The default standalone ledger now rejects legacy pending-location, voice-recovery, effect-recovery, and staff-queue methods before reading their rich rows; `test/storage/standalone-ledger-read-gate.test.ts` probes these against synthetic patient-bearing legacy rows. Those old rows still require disposal or migration before real traffic.

## Current code gap

The reference PostgreSQL ledger still serializes rich `calls.state`, `effect_outbox.payload`, and `staff_items.payload` values. A disposable PostgreSQL journey found exact synthetic offer references in `calls.state` and `effect_outbox.payload`, and an appointment reference in `calls.state` and `staff_items.payload`. Those tests now select the explicitly named `unsafeReference` ledger mode; the default mode and production standalone text composition use a named-field state projection. That projection drops caller messages, greeting and presentation text, knowledge-answer history, and availability/appointment read history before writing `calls.state`; it rejects action, staff, and effect payloads, and it disallows voice admission until a privacy-safe voice design is implemented. It accepts only UUID-v4-shaped call and turn IDs; the caller ingress must still prove those IDs are generated independently of patient content. The focused PostgreSQL E2E sees transient answer text but no caller, answer, greeting, or rejected turn-ID canary in Abby's tables. The database-wide scanner returns only table and column names, never stored values.

The production standalone composition constructs an internal disabled host instead of requiring a synthetic reference host. It still fixes booking, cancellation, rescheduling, intake, and transfer to `unavailable`, disables staff-task intents, and does not accept appointment or model adapters. It may attach only a Cliniko availability reader for provisional, read-only times; the text-only call ledger drops shown times and speech before persistence, and the synthetic PostgreSQL agent journey scans for those canaries. A one-attempt Cliniko recall writer can put request text in Cliniko notes and a bounded reader can observe the exact patient, marker, notes, recall type, and due date; neither is connected to production task commands, and a read miss never permits retrying an uncertain create. The product owner kept patient-specific handoff disabled for the first Cliniko-only release until a clinic approves the workflow (D-07). Abby does not yet have an approved Cliniko-owned task workflow, an action seam, an approved caller-verification flow, or a real telephony adapter. Existing rich rows need disposal or migration before a database can be used for real traffic: the strict reader rejects them but does not erase them. The PostgreSQL policy store now defaults to minimal booking-setting rows containing only scope, version, and the boolean toggle, with staff work disabled; synthetic rich-policy tests explicitly request `unsafeReference`. The production composition does not attach PostgreSQL knowledge and returns no approved knowledge until a safe content source exists. Direct construction of the PostgreSQL knowledge catalogue now defaults to disabled reads and writes; synthetic reference fixtures explicitly select `unsafeReference`. Strict write-stop rows accept only `cutover` or `operatorStop` when stopped and `operatorResume` when resumed; portability-fence rows accept only `cutoverFreeze` or `cutoverRelease` for their matching transitions. These operational codes block patient text at those write boundaries, and PostgreSQL E2E scans for rejected canaries. The default configuration archive carries only minimal setting history and rejects rich policies, knowledge rows, and nonconforming write-stop reason history; synthetic reference rehearsals opt into the legacy rich format explicitly. The PostgreSQL tenant importer now defaults to accepting only minimal policy rows with no knowledge, stores only minimal policy JSONB, maps disabled reference placeholders to a fixed code, and creates a `cutover` write stop; synthetic rich imports explicitly opt into `unsafeReference`. The legacy/reference storage classes, existing rich settings and knowledge rows, logs, backups, and failed/retried paths still need the complete patient-data gate. A text classifier cannot prove arbitrary free text is patient-free, so a constrained clinic-content workflow or host-owned storage is required before real traffic. The projection is a text-only call-ledger slice, not a full privacy pass. The 100,000-patient and 100,000-link scan limits still fail closed for larger clinics. The current code must not be enabled for real patient calls. Caller-turn text digests have been removed from new states and scrubbed from legacy rows; replay uses only a stable turn ID. The next implementation slice is a broader E2E storage gate; Cliniko-owned task commands remain gated on clinic workflow approval.
